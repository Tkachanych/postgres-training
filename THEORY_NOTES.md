### №1 — 2026-10-31 — NULL-семантика: `EXISTS` / `NOT EXISTS` / `IN` / `NOT IN` / `IS [NOT] DISTINCT FROM`

**Разобрали:**
- `IN` — сравнение значений (`= ANY`), `EXISTS` — проверка факта строки (короткое замыкание, неважно, что в `SELECT`).
- Трёхзначная логика: `WHERE` пропускает только `TRUE`, `FALSE` и `UNKNOWN` отбрасываются.
- Ловушка `NOT IN`: один `NULL` в наборе делает предикат `UNKNOWN` для всех строк → пустой результат.
- `x NOT IN (пустой набор)` = `TRUE` → возвращаются **все** строки (обратный крайний случай).
- `NOT IN` по подзапросу с `NULL` — нелокальная молчаливая ошибка: ломается не сразу, а когда NULL появится в данных.
- `IS [NOT] DISTINCT FROM` — NULL-безопасное сравнение, никогда не даёт `UNKNOWN`; `NULL IS NOT DISTINCT FROM NULL` = `TRUE`.
- Планировщик: `NOT EXISTS` всегда можно превратить в anti-join; `NOT IN` — только если набор доказуемо без NULL (`NOT NULL`, фильтр, литералы).
- `IS [NOT] DISTINCT FROM` не использует btree-индекс (нет оператора). Ускорение: `COALESCE` + expression/partial index или `UNION ALL` по веткам (не-NULL и оба NULL).
- `UNION ALL`, а не `UNION`: дедупликация меняет семантику и дорога.
- `COALESCE` выводит тип статически (по всем аргументам), а не «по первому значению»; главный риск sentinel-значения — коллизия с реальным `id`.
- NULL во внешней колонке: `NOT IN` отбрасывает строку (`UNKNOWN`), `NOT EXISTS` включает.

**Edge-кейсы для повторения:**
- `x IN (1, NULL)` = `UNKNOWN`, но совпадающие значения всё равно проходят (`IN` — это `OR`).
- `x NOT IN (1, NULL)` = `UNKNOWN` всегда → `TRUE` недостижим (`NOT IN` — это `AND`).
- `NOT (x = 1)` ≠ `x IS DISTINCT FROM 1` (первое даёт `UNKNOWN` для `x IS NULL`).
- `x IS DISTINCT FROM 1` ⟺ `x <> 1 OR x IS NULL`.

**На что обратить внимание при повторении:**
- Путал направление `DISTINCT`: `IS NOT DISTINCT FROM` = «`=` null-safe», `IS DISTINCT FROM` = «`<>` null-safe».
- Сначала говорил, что `IN` возвращает `FALSE` — на самом деле `UNKNOWN`; вывод «строка не прошла» тот же, но значение другое.
- В `NOT IN` подзапросе писал `SELECT 1` вместо `SELECT user_id` — сравнивал с константой, а не с ключом.
- Критерий выбора `IS DISTINCT FROM` — семантика (NULL как значение), а не «не нужен индекс»; отсутствие индекса — это цена.

### №2 — 2026-11-01 — Semi join и anti join: логика, формы записи, планы, NULL-ловушки

**Что разобрали:**
- Semi join — «существует ли пара»: строки `A` с хотя бы одним совпадением в `B`, только колонки `A`, каждая строка `A` не более одного раза.
- Anti join — «нет ли пары»: строки `A` без совпадений в `B`, тоже без размножения.
- Обычный `JOIN` — умножение (1:N → N строк); semi/anti — предикат существования (1:0..N → 1 или 0).
- Формы semi: `EXISTS`, `IN`/`= ANY`, `JOIN + DISTINCT`, `LATERAL ... LIMIT 1`.
- Формы anti: `NOT EXISTS`, `LEFT JOIN ... WHERE b.key IS NULL`, `EXCEPT`, `NOT IN`/`<> ALL`.
- Для semi `IN` и `EXISTS` в `WHERE` эквивалентны по результату даже при NULL: `UNKNOWN` отфильтровывается, нужен только `TRUE`. NULL-проблема — только у `NOT IN`.
- `NOT EXISTS` null-safe по построению: `b.x = NULL` не `TRUE` → совпадения нет → строка `A` проходит.
- `NOT IN` с `NULL` в подзапросе даёт `UNKNOWN` → строка молча теряется.
- `EXCEPT` — множественная операция: дедуплицирует и считает `NULL = NULL` (`IS NOT DISTINCT FROM`), семантика не равна anti-join.
- `LEFT JOIN ... IS NULL` корректен только при `NOT NULL` на проверяемой колонке `B`; на дублях `B` размножает промежуточные строки.
- Планировщик распознаёт `EXISTS`/`NOT EXISTS` и строит `Hash/Nested Loop/Merge Semi Join` и `Hash/Merge Anti Join`.
- Semi join короткозамыкается на первом совпадении; anti join обязан убедиться в отсутствии совпадений.
- Semi/anti join не коммутативны как inner join — планировщику труднее переставлять стороны.
- `NOT IN` обычно не превращается в anti join из-за NULL-семантики (остаётся `SubPlan`/`hashed SubPlan`).
- `EXISTS (SELECT 1 ...)` и `EXISTS (SELECT * ...)` эквивалентны — список `SELECT` в `EXISTS` не вычисляется.

**Ключевые выводы:**
- Мантра: semi — «есть ли», anti — «нет ли»; semi пиши `EXISTS`, anti пиши `NOT EXISTS`; `NOT IN` — только при гарантированном `NOT NULL` с обеих сторон.
- `JOIN + DISTINCT` для semi — антипаттерн: материализует дубли и дедуплицирует.
- `EXCEPT` для anti — перебор: хеширует/сортирует оба набора без раннего выхода и меняет семантику (NULL, дубли).
- Индекс под anti — по соединяемой колонке `B` (`b.a_id`), а не по `A`; для дополнительных условий — составной/partial.
- `Hash Anti Join` хорошо масштабируется на больших `B`, `Nested Loop Anti Join` + индекс — когда `A` мала/селективна.

**Edge-кейсы:**
- NULL в ключе `A`: `NOT EXISTS` вернёт строку, `NOT IN` — нет. Разные результаты на одних данных.
- Дубли в `B`: `EXISTS`/`NOT EXISTS` не чувствительны; `LEFT JOIN IS NULL` размножает; `IN` — ок.
- Составной ключ: `(a.x, a.y) NOT IN (...)` — двойная NULL-ловушка; `NOT EXISTS` с `AND` по колонкам безопаснее.
- Semi join не отдаёт колонки `B`: нужны — `DISTINCT ON` или `LATERAL ... LIMIT 1`.
- `OR` в коррелированном условии может блокировать превращение в anti join.
- `<> ALL`/`NOT IN` — одно семейство ловушек с NULL.

**Слабые места ученика:**
- NULL-ловушку сначала объяснял только через `a.id IS NULL`, упуская `NULL` в выводе подзапроса; semi-эквивалентность `IN`/`EXISTS` сформулировал частично.
- В `NOT IN`-переписывании отфильтровал `o.id` (PK, всегда `NOT NULL`) вместо `o.user_id` — невнимательность к тому, какой столбец реально содержит NULL.
- Считал, что `LEFT JOIN ... IS NULL` увеличивает **итоговый** результат на дублях `B`; на самом деле размножается только промежуточный join, итог корректен при `NOT NULL` на проверяемой колонке.
- В вопросе про планировщик назвал только подзапросную сторону NULL, упустив левое выражение (`a.id`).
- Не разобрал третий вариант `u.id IS NULL OR u.id NOT IN (...)` — компенсацию NULL слева через явное `OR`.

**Вопросы для самопроверки:**
1. Почему `IN` в `WHERE` можно заменить на `EXISTS` при NULL в подзапросе, а `NOT IN` — нельзя? (через `TRUE`/`UNKNOWN`)
2. Anti-join «пользователи без заказов», `orders.user_id NOT NULL`, но `users.id` бывает `NULL`: что вернут `NOT EXISTS`, `NOT IN`, `LEFT JOIN ... IS NULL`?
3. Чем `EXCEPT` отличается от `NOT EXISTS` по семантике (NULL, дубли) и по стоимости?
4. Какой индекс нужен под `NOT EXISTS` и почему не по `A`?

### №3 — 2026-11-09 — Статистика планировщика и VACUUM: актуальность, autovacuum, bloat, freeze, мониторинг

**Разобрали:**
- Два разных смысла «статистики»: статистика планировщика (`pg_statistic` / `pg_stats`, обновляется `ANALYZE`) и кумулятивные счётчики `pg_stat_*` для мониторинга. Это не одно и то же, и `VACUUM` сам по себе не обновляет статистику планировщика.
- Планировщик cost-based: выбирает план по оценке кардинальности (сколько строк вернёт каждый шаг), а не по фактическим данным. Плохая оценка → плохой join order / метод соединения / индекс.
- Что лежит в `pg_stats`: `null_frac`, `avg_width`, `n_distinct`, `most_common_vals` + `most_common_freqs` (MCV), `histogram_bounds`, `correlation`.
- `n_distinct`: положительное — абсолютное число, отрицательное — доля от числа строк (−1 ≈ уникальная колонка); после `ANALYZE` оценка масштабируется под текущий размер таблицы.
- `correlation` — насколько физический порядок строк совпадает с логическим; высокая корреляция делает index scan дешёвым, низкая — дорогим (random I/O).
- `ANALYZE` читает выборку, а не всю таблицу: примерно `300 * default_statistics_target` строк (по умолчанию target = 100). Это быстро, но при редких/скошенных значениях оценка может быть грубой.
- Устаревание статистики: массовая загрузка, массовое удаление, смена распределения, новый партишн. Autovacuum ANALYZE срабатывает при изменении > `50 + 10%` строк (`autovacuum_analyze_threshold` / `autovacuum_analyze_scale_factor`).
- Массовую загрузку нужно сопровождать ручным `ANALYZE` (или `VACUUM ANALYZE`), не надеясь на autovacuum «когда-нибудь».
- Тонкая настройка статистики: `ALTER TABLE ... ALTER COLUMN ... SET STATISTICS N` для проблемных колонок, `default_statistics_target` глобально; extended statistics (`CREATE STATISTICS ... (dependencies, ndistinct, mcv)`) для коррелированных колонок и функциональных зависимостей.
- MVCC: `UPDATE` = новая версия + мёртвая старая, `DELETE` = мёртвая версия; индексы тоже накапливают ссылки на мёртвые версии.
- `VACUUM` (обычный): освобождает место **внутри** relation для повторного использования, обновляет FSM, visibility map и freeze-информацию; не возвращает место ОС (кроме усечения пустых страниц в конце), не сжимает файл, не перестраивает индексы; блокировка `SHARE UPDATE EXCLUSIVE`, DML не блокируется.
- `VACUUM FULL`: переписывает таблицу и индексы, возвращает место ОС, но берёт `ACCESS EXCLUSIVE` (полный простой) и требует свободного места примерно на размер таблицы. Не рутинная операция; альтернатива — `pg_repack`.
- Autovacuum — это launcher + worker-процессы. Порог: мёртвых строк > `50 + 20%` (`autovacuum_vacuum_threshold` / `autovacuum_vacuum_scale_factor`), проверка раз в `autovacuum_naptime`, workers по умолчанию 3.
- Visibility map: страница «all-visible» → index-only scan может не ходить в heap. `VACUUM` заполняет VM, поэтому после вакуума index-only scan может ускориться, хотя размер файла не изменился.
- Freeze и wraparound: 32-битный счётчик транзакций, `relfrozenxid`, `age(relfrozenxid)`; при превышении `autovacuum_freeze_max_age` (200 млн) запускается aggressive vacuum; в пределе — защита от потери данных и остановка записи.
- Что мешает vacuum убирать мёртвые строки: долгие транзакции, `idle in transaction`, подготовленные транзакции (2PC), replication slots, удерживающие старый `xmin`. Пока snapshot видит строку, vacuum её не удалит.
- Мониторинг: `pg_stat_user_tables` (`n_live_tup`, `n_dead_tup`, `n_mod_since_analyze`, `last_*`, `*_count`), `pg_stat_progress_vacuum`, `pg_stat_activity` (`xact_start`, `backend_xmin`), `pg_stat_replication`, `pg_database` (`age(datfrozenxid)`).
- `VACUUM`/`ANALYZE` нельзя выполнять внутри транзакционного блока; для партиционированных таблиц autovacuum обрабатывает партиции по отдельности — не полагаться только на обслуживание родителя.

**Edge-кейсы для повторения:**
- Пустая или очень маленькая таблица: autovacuum-порог в процентах почти не срабатывает, а `n_dead_tup` может быть мал — но и вреда немного; важнее не отключать autovacuum совсем.
- `n_dead_tup` в `pg_stat_*` — приблизительный счётчик, а не точная инвентаризация bloat.
- Таблица с высокой корреляцией колонки и индекса: seq scan может быть выгоднее index scan, и это не «плохой план».
- `VACUUM FULL` на большой таблице может упасть по диску в самый неподходящий момент: нужен запас и план.
- После `VACUUM` место не уменьшилось — это норма, а не ошибка; «раздутость» лечится `VACUUM FULL`/`pg_repack` или перестройкой.
- Долгая транзакция «в отпуске» (idle in transaction) незаметно держит vacuum и приводит к bloat и wraparound-рискам.
- Rare values: без MCV/гистограммы планировщик может оценить редкое значение как частое; тогда поможет повышение target или extended statistics.

**Слабые места ученика:**
- Первое занятие по теме — диагностика появится на следующих сессиях.

**Дополнение по проверке понимания (2026-11-09):**
- Ответ 1: верное направление — планировщик не знает распределения новых строк, потому что `ANALYZE` не было. Но названы не все механизмы: устаревает не только `null_frac`/`correlation`, а в первую очередь селективность предикатов по новым значениям (MCV/гистограмма) и оценка числа строк (`pg_class.reltuples` обновляется только `VACUUM`/`ANALYZE`). Прирост на 10% сам по себе редко ломает план — ломает неверная селективность (новое скошенное значение, новая партиция, изменившееся распределение). Диагностика: `n_mod_since_analyze`, `last_analyze`/`last_autoanalyze`, сравнение `reltuples` с `n_live_tup`, `EXPLAIN (ANALYZE, BUFFERS)` — оценка `rows` против факта.
- Ответ 2: механизм перепутан. `VACUUM` не «помечает» строки — они уже мертвы по `xmax`; он физически удаляет мёртвые версии, освобождает место в страницах (line pointer → unused), обновляет FSM/VM и замораживает XID. Visibility map — не инструмент поиска мёртвых строк для vacuum, а результат его работы: бит all-visible позволяет index-only scan не ходить в heap. Если страница не all-visible, IOS идёт в heap проверить видимость. Статистика планировщика к VM и проверке видимости отношения не имеет — она влияет только на выбор плана.
- Слабые места: путаница между «статистика для оценки стоимости» и «видимость строк / visibility map»; не назван `reltuples` как отдельный источник устаревшей оценки; механизм IOS описан наоборот (VM как обязательная проверка вместо оптимизации).

**Дополнение по второй проверке (2026-11-09):**
- Ответ 1: итог верный (место переиспользуется, файл не уменьшается), но терминология неточная. `VACUUM` не «помечает мёртвую версию как unused»: он удаляет tuple физически, а unused становится **line pointer** (item identifier), который потом переиспользуется под новую строку на этой же странице. Данные внутри страницы удаляются, но сама страница остаётся выделенной в файле — поэтому размер не уменьшается (в ответе было «не увеличивается»). Пустые страницы в хвосте relation могут усекаться, но это частичный возврат места.
- Ответ 2: верно про all-visible, но неполно. IOS дополнительно требует covering index (все нужные колонки есть в индексе) и поддержки со стороны AM; в heap он идёт, когда бит all-visible сброшен — например, после свежего `INSERT`/`UPDATE` на странице. Бит all-frozen для видимости не нужен. Статистика планировщика влияет на выбор IOS как плана, но не на постраничную проверку VM.
- Слабые места: смешение уровня «tuple vs line pointer vs page»; не назван covering index как условие IOS; не указано, что бит all-visible сбрасывается при изменении страницы.
- Следующие вопросы: глобальный `xmin` и долгие транзакции; диагностика bloat без `VACUUM FULL`.

**Уточнение по третьему кругу (2026-11-09):**
- Вова засомневался, что обычный `VACUUM` физически удаляет данные, и связал физическое удаление только с `VACUUM FULL` или усечением последней страницы. Развели три уровня: tuple (удаляется обычным `VACUUM`), страница (остаётся в файле, место переиспользуется; пустые страницы в хвосте могут усекаться), relation/файл (не сжимается; `VACUUM FULL`/`CLUSTER`/`pg_repack` переписывают relation и возвращают место ОС).
- Ключевое: `VACUUM` компактирует содержимое страницы (удаляет мёртвые tuple, уплотняет живые, чинит line pointers, обновляет FSM/VM), но не переносит живые tuple между страницами, поэтому дырки в середине файла не схлопываются.
- Слабое место: смешение «удаление tuple» и «уменьшение файла»; не учитывалось, что `VACUUM` физически переписывает страницы, хотя и не меняет их количество.

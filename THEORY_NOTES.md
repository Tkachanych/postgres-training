### №1 — 2026-10-31 — NULL-семантика: `EXISTS` / `NOT EXISTS` / `IN` / `NOT IN` / `IS [NOT] DISTINCT FROM`

**Разобрали:**
- `IN` — сравнение значений (`= ANY`), `EXISTS` — проверка факта строки (короткое замыкание, неважно, что в `SELECT`).
- Трёхзначная логика: `WHERE` пропускает только `TRUE`, `FALSE` и `UNKNOWN` отбрасываются.
- Ловушка `NOT IN`: один `NULL` в наборе делает предикат `UNKNOWN` для всех строк → пустой результат.
- `x NOT IN (пустой набор)` = `TRUE` → возвращаются **все** строки (обратный крайний случай).
- `NOT IN` по подзапросу с `NULL` — нелокальная молчаливая ошибка: ломается не сразу, а когда NULL появится в данных.
- `IS [NOT] DISTINCT FROM` — NULL-безопасное сравнение, никогда не даёт `UNKNOWN`; `NULL IS NOT DISTINCT FROM NULL` = `TRUE`.
- Планировщик: `NOT EXISTS` всегда можно превратить в anti-join; `NOT IN` — только если набор доказуемо без NULL (`NOT NULL`, фильтр, литералы).
- `IS [NOT] DISTINCT FROM` не использует btree-индекс (нет оператора). Ускорение: `COALESCE` + expression/partial index или `UNION ALL` по веткам (не-NULL и оба NULL).
- `UNION ALL`, а не `UNION`: дедупликация меняет семантику и дорога.
- `COALESCE` выводит тип статически (по всем аргументам), а не «по первому значению»; главный риск sentinel-значения — коллизия с реальным `id`.
- NULL во внешней колонке: `NOT IN` отбрасывает строку (`UNKNOWN`), `NOT EXISTS` включает.

**Edge-кейсы для повторения:**
- `x IN (1, NULL)` = `UNKNOWN`, но совпадающие значения всё равно проходят (`IN` — это `OR`).
- `x NOT IN (1, NULL)` = `UNKNOWN` всегда → `TRUE` недостижим (`NOT IN` — это `AND`).
- `NOT (x = 1)` ≠ `x IS DISTINCT FROM 1` (первое даёт `UNKNOWN` для `x IS NULL`).
- `x IS DISTINCT FROM 1` ⟺ `x <> 1 OR x IS NULL`.

**На что обратить внимание при повторении:**
- Путал направление `DISTINCT`: `IS NOT DISTINCT FROM` = «`=` null-safe», `IS DISTINCT FROM` = «`<>` null-safe».
- Сначала говорил, что `IN` возвращает `FALSE` — на самом деле `UNKNOWN`; вывод «строка не прошла» тот же, но значение другое.
- В `NOT IN` подзапросе писал `SELECT 1` вместо `SELECT user_id` — сравнивал с константой, а не с ключом.
- Критерий выбора `IS DISTINCT FROM` — семантика (NULL как значение), а не «не нужен индекс»; отсутствие индекса — это цена.

### №2 — 2026-11-01 — Semi join и anti join: логика, формы записи, планы, NULL-ловушки

**Что разобрали:**
- Semi join — «существует ли пара»: строки `A` с хотя бы одним совпадением в `B`, только колонки `A`, каждая строка `A` не более одного раза.
- Anti join — «нет ли пары»: строки `A` без совпадений в `B`, тоже без размножения.
- Обычный `JOIN` — умножение (1:N → N строк); semi/anti — предикат существования (1:0..N → 1 или 0).
- Формы semi: `EXISTS`, `IN`/`= ANY`, `JOIN + DISTINCT`, `LATERAL ... LIMIT 1`.
- Формы anti: `NOT EXISTS`, `LEFT JOIN ... WHERE b.key IS NULL`, `EXCEPT`, `NOT IN`/`<> ALL`.
- Для semi `IN` и `EXISTS` в `WHERE` эквивалентны по результату даже при NULL: `UNKNOWN` отфильтровывается, нужен только `TRUE`. NULL-проблема — только у `NOT IN`.
- `NOT EXISTS` null-safe по построению: `b.x = NULL` не `TRUE` → совпадения нет → строка `A` проходит.
- `NOT IN` с `NULL` в подзапросе даёт `UNKNOWN` → строка молча теряется.
- `EXCEPT` — множественная операция: дедуплицирует и считает `NULL = NULL` (`IS NOT DISTINCT FROM`), семантика не равна anti-join.
- `LEFT JOIN ... IS NULL` корректен только при `NOT NULL` на проверяемой колонке `B`; на дублях `B` размножает промежуточные строки.
- Планировщик распознаёт `EXISTS`/`NOT EXISTS` и строит `Hash/Nested Loop/Merge Semi Join` и `Hash/Merge Anti Join`.
- Semi join короткозамыкается на первом совпадении; anti join обязан убедиться в отсутствии совпадений.
- Semi/anti join не коммутативны как inner join — планировщику труднее переставлять стороны.
- `NOT IN` обычно не превращается в anti join из-за NULL-семантики (остаётся `SubPlan`/`hashed SubPlan`).
- `EXISTS (SELECT 1 ...)` и `EXISTS (SELECT * ...)` эквивалентны — список `SELECT` в `EXISTS` не вычисляется.

**Ключевые выводы:**
- Мантра: semi — «есть ли», anti — «нет ли»; semi пиши `EXISTS`, anti пиши `NOT EXISTS`; `NOT IN` — только при гарантированном `NOT NULL` с обеих сторон.
- `JOIN + DISTINCT` для semi — антипаттерн: материализует дубли и дедуплицирует.
- `EXCEPT` для anti — перебор: хеширует/сортирует оба набора без раннего выхода и меняет семантику (NULL, дубли).
- Индекс под anti — по соединяемой колонке `B` (`b.a_id`), а не по `A`; для дополнительных условий — составной/partial.
- `Hash Anti Join` хорошо масштабируется на больших `B`, `Nested Loop Anti Join` + индекс — когда `A` мала/селективна.

**Edge-кейсы:**
- NULL в ключе `A`: `NOT EXISTS` вернёт строку, `NOT IN` — нет. Разные результаты на одних данных.
- Дубли в `B`: `EXISTS`/`NOT EXISTS` не чувствительны; `LEFT JOIN IS NULL` размножает; `IN` — ок.
- Составной ключ: `(a.x, a.y) NOT IN (...)` — двойная NULL-ловушка; `NOT EXISTS` с `AND` по колонкам безопаснее.
- Semi join не отдаёт колонки `B`: нужны — `DISTINCT ON` или `LATERAL ... LIMIT 1`.
- `OR` в коррелированном условии может блокировать превращение в anti join.
- `<> ALL`/`NOT IN` — одно семейство ловушек с NULL.

**Слабые места ученика:**
- NULL-ловушку сначала объяснял только через `a.id IS NULL`, упуская `NULL` в выводе подзапроса; semi-эквивалентность `IN`/`EXISTS` сформулировал частично.
- В `NOT IN`-переписывании отфильтровал `o.id` (PK, всегда `NOT NULL`) вместо `o.user_id` — невнимательность к тому, какой столбец реально содержит NULL.
- Считал, что `LEFT JOIN ... IS NULL` увеличивает **итоговый** результат на дублях `B`; на самом деле размножается только промежуточный join, итог корректен при `NOT NULL` на проверяемой колонке.
- В вопросе про планировщик назвал только подзапросную сторону NULL, упустив левое выражение (`a.id`).
- Не разобрал третий вариант `u.id IS NULL OR u.id NOT IN (...)` — компенсацию NULL слева через явное `OR`.
